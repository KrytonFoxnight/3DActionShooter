# 플레이어 구조 결정: 순수 C# 중앙화 vs 기능 단위 컴포넌트 분리

이 문서는 전투 시스템 착수 시점(2026-08-01)에 내린 플레이어 아키텍처 방향에 대한 고민과 그 근거를 기록합니다.

- 결정: 사전에 결정했던 방식대로 **기능 단위 Unity 컴포넌트 분리 + 계산·규칙만 순수 C#** 로 진행함.
- 기각: 중앙 `Player.cs` + 게임 로직 전면 순수 C#화 (방식 A)

## 1. 비교한 두 방식

### 방식 A — 중앙화 + 전면 순수 C# (대형사/라이브 서비스 실무 관례)

```text
Player : MonoBehaviour  (단일 진입점, 씬 어댑터)
  ├─ field: PlayerHealth   (순수 C#)
  ├─ field: PlayerMovement (순수 C#)
  ├─ field: PlayerAttack   (순수 C#)
  └─ Update()에서 순수 레이어를 구동, 결과를 엔진에 반영
```

- 게임 로직을 가능한 한 엔진 무관한 순수 C#으로 두어 테스트 용이성을 확보하고자 함
- Unity와는 중간 MonoBehaviour 스크립트 어댑터로 연결
- 중앙 클래스가 모든 기능의 참조를 소유하고 조율한다. 외부 시스템은 `Player` 하나만 알면 된다.
- 기존 실무 프로젝트에서 따르던 방식.

**장점**

- 외부 시스템이 플레이어를 단일 진입점 하나로 다룸
- 게임 로직이 엔진 독립적이므로 서버 권위 구조에서 그대로 이식 가능함
- 실행 순서를 중앙에서 통제 — 컴포넌트 간 암묵적 순서 의존이 없음
- 병렬 작업·코드 리뷰에 유리 (게임 로직이 씬이 아닌 코드에 있으므로)

**단점**

- 이중 구조 유지 비용
- 허브가 모든 기능의 접착제가 되어 비대해지기 쉬움 (갓클래스 위험, 실무 프로젝트에서도 해당 문제 있었음)
- 엔진의 컴포넌트 모델과 마찰 — 인스펙터·프리팹·`RequireComponent` 활용도가 낮음

### 방식 B — 기능 단위 컴포넌트 분리

```text
Player GameObject  (정체성은 GameObject/프리팹에 있음)
  ├─ PlayerMovement    : MonoBehaviour   (이동/점프/대시)
  ├─ PlayerInputReader : MonoBehaviour   (입력 창구)
  ├─ PlayerHealth      : MonoBehaviour, IDamageable ── Health(순수 C#)를 소유
  └─ PlayerMeleeAttack : MonoBehaviour   (히트박스 판정)

순수 C#은 계산·규칙에 한정: Health, (4주차) 데미지 계산 파이프라인
```

- 각 기능이 독립 MonoBehaviour로 GameObject에 병렬로 붙음
- 각 컴포넌트는 자기에게 필요한 이웃만 `GetComponent` 또는 SerializeField로 관리
- 순수 C# 분리는 전면이 아니라 **계산과 규칙이 있는 지점에만** 적용

**장점**

- Unity Engine의 설계 방식과 유사함
- 기능 단위로 재사용 및 Toggle 가능 (`Health`를 적에게 재사용, 사망 시 이동만 끄기)
- 파일들이 역할별로 작게 유지되고 초기 개발 속도가 빠름

**단점**

- 중앙화된 창구가 없어, 외부 조율 요구가 생기면 참조가 흩어짐 (보상 시스템 등에서 얇은 허브 추가 검토)
- 별도 초기화 규칙이 없다면 컴포넌트 간 참조와 실행 순서가 보장되지 않을 수 있음 (Unity 생명주기의 우선순위 주입이 있긴 하지만 분산되어있어서 여전히 위험할 수 있음)
- 엔진 종속성이 A안보다 강해서 테스트 가능한 범위가 계산 레이어(`Health` 등)로 한정됨

## 2. 방식 B를 택한 이유

### 이유 1: A안(전면 순수 C#화)의 이점이 사이드 프로젝트에 유의미하지 않다고 판단
- 기존 실무 프로젝트와 달리 Unity Engine 기능들을 활용하는 것이 더 중요함 (CharacterController, Physics, 3D Camera Movement 등)
- 이 프로젝트에서 필요한 기능 단위 구현에서 B안이 더 나은 선택지임

### 이유 2: Unity에서 제공하는 오픈 프로젝트의 구조가 방식 B에 기울어져 있음
- 두 프로젝트 모두 전면 순수 C#화는 하지 않았음
- 오픈 프로젝트들의 완성도와 이 프로젝트에서 요구하는 완성도 수준을 고려했을때 전면 C#화는 과잉
- 인스펙터, 프리팹, 기능 단위의 비활성화 등이 별도의 작업 없이 동작 가능

## 3. 엔진이 제공해주는 영역은 활용하고, 게임 시스템에서만 필요한 부분만 순수 처리

- 기존 실무 프로젝트는 게임 장르 특성 상 효과 시뮬레이션이 주된 로직이었기 때문에, Unity Engine에서 제공되는 각종 기능들을 활용할 여지가 드물었음.
- 따라서 이번 프로젝트에서는 **엔진이 이미 잘하는 일은 별도 사유가 없다면 기존 기능을 활용하며, 게임의 규칙과 수치 계산처럼 완전히 새로 구현해야 하는 시스템만 순수 C#으로 작성** 하는 방향으로 결정함.
- 단, Camera 관련 시스템은 Cinemachine이 있었으나, NDC에서 들었던 마비노기 카메라 시스템의 구현 경험 및 학습을 위하여 의도적으로 제외했다.

```text
순수 C# (규칙·수치)                엔진 네이티브 (공간·물리·연출)
────────────────────              ────────────────────────────
Health (구현 완료)                 이동/중력 (CharacterController)
데미지 계산 파이프라인               히트 판정 (Physics 쿼리)
  (4주차, 보상 배율 적용부)          카메라, 애니메이션
웨이브 구성 규칙 (후보)              적 AI 조향, 스폰 오브젝트
```
