# 캐릭터 종속 UI 결정: 스크린스페이스 투영 vs 월드스페이스 Canvas

이 문서는 적 체력바 구현 시점(2026-08-27)에 선택한 **3D 캐릭터에 종속되는 UI의 배치 방식**을 기록합니다.

- 채택: **씬 공용 스크린스페이스 Canvas + `WorldToScreenPoint` 투영**
- 기각: 캐릭터 프리팹 자식으로 붙는 월드스페이스 Canvas

## 1. 채택안의 구조

구현 계층이 셋으로 분할되며, **유닛들의 프리팹에는 Canvas가 붙지 않습니다.** 핸들러 스크립트만 붙고 UI 오브젝트는 공용 overlay Canvas 밑에서 생성 및 관리됩니다.

| 조각   | 역할                                           | 위치              |
|------|----------------------------------------------|-----------------|
| 공용 Canvas | 체력바 UI만 그림                                   | 씬에 하나           |
| View | 체력바 UI 인스턴스 하나. 받은 값을 반영만 하고 스스로 판단하지 않음 | 공용 Canvas의 자식으로 생성 |
| 핸들러  | 유닛에 부착되어 View의 화면 위치를 갱신하고, 체력 변화를 받아 View에 전달 | 유닛 Prefab       |

## 2. 해당 방식을 채택한 이유

1. 단일 overlay Canvas에서 중앙 관리하는 방식이 Drawcall과 리빌드 양쪽에서 유리합니다. 같은 구조를 Boss Room에서도 확인했으며, 코드를 옮겨오지 않고 이 프로젝트 규모에 맞게 직접 구현했습니다(5절).
2. UGUI의 리빌드 단위가 Canvas 전체이므로, Dynamic & Static 기준의 Canvas 구분이 중요합니다. 체력바는 피격마다 바뀌는 가장 시끄러운 UI여서, 정적 HUD와 같은 Canvas에 두면 적이 맞을 때마다 정적 요소까지 재구축됩니다.

## 3. 다른 방식을 채택하지 않았던 이유

1. **배칭은 Canvas 단위로 끊깁니다.** material·texture가 같아도 Canvas가 다르면 병합되지 않으며, Canvas마다 최소 1 Drawcall이 깔립니다. 추후 유닛 분량이 증가할 때마다 Canvas 연산 비용 또한 선형적으로 같이 증가합니다.
2. **화면 밖 Canvas도 Drawcall을 소비하므로 다수 유닛에 대한 성능 문제가 있습니다.**
3. UI가 월드 스케일로 Rasterize되므로 **텍스트 등 가시적 표현에서 뭉개지는 등의 문제가 발생할 수 있습니다.**
4. 3D에 실재하므로 **매 프레임 카메라를 향해 회전**시키는 별도의 빌보드 처리를 해야합니다. 기능 구현에 있어 과도한 구현 방식입니다.

## 4. 규모가 아니라 기회비용

동시 등장 적이 5마리 수준이므로 3절의 비용은 지금 발생하지 않습니다. 그럼에도 채택안으로 간 이유는 확장 대비가 아니라, 이 저장소가 2026-08-27에 코드 작업을 종료하여 **전환 시점 자체가 존재하지 않기** 때문입니다. 월드스페이스를 전제로 프리팹 계층과 스포너·풀링 배선이 굳고 나면 전환은 코드가 아니라 구조를 건드리는 작업이 되며, 그 비용이 지금 짓는 비용보다 큽니다.
